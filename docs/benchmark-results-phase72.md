- Candidate under evaluation: **pdfjs-dist 6.3.289** (Apache-2.0, devDependency,

## 2. Benchmark corpus (§4–§6)

39 synthetic fixtures (v2), all generated in memory by repository-owned
builders (`src/lib/benchmarks/fixtures.ts`):

- **Text (10)**: single/multi-page, short/long paragraphs, multiple fonts,
  font sizes 8–36 pt, bold/italic, accented Latin (é ï ö ü å ç ß), WinAnsi
  symbols (© ® ° ± × ÷ ½ ¼ € µ), numbers, punctuation, unusual whitespace.
- **Layout (8)**: two-column, three-column, header/footer/page numbers,
  scrambled draw order, positioned labels, overlapping text, 90° rotated
  text, landscape, unusual page dimensions (200×300 and 1400×900).
- **Pages (3)**: 2, 10, 30 and a bounded 50-page stress document (at the
  current engine's page limit).
- **Images (3)**: text+image, image-only (deterministic noise "scan"),
  multiple images.
- **Tables (5)**: aligned 4×3, 10×3, 4×6, 12×3 split across pages, and
  6×3 with each cell a separate positioned text run.
- **Edge (5)**: blank PDF, blank page among text, malformed bytes,
  truncated (valid PDF cut at 50%), 400-object dense page, off-page text
  (glyphs extending past the page edge).

Every fixture carries machine-readable provenance (`generator`,
`synthetic: true`, `copyright`, `provenance`), characteristics tags, and
explicit ground truth from the fixture definition itself (pages, ordered
anchors, tokens, character counts, table cells, blank pages, unicode/symbol
characters, image counts, page dimensions). Ground truth was cross-checked
against pdf-lib page/dimension parsing — never against an engine's output.
No copyrighted material, no customer documents, no PII, no
decompression bombs, no resource-exhausting payloads.

Corpus limitations (documented, not hidden): **no Tamil fixture** (pdf-lib
standard-14 fonts are WinAnsi-encoded; Tamil requires embedding an OFL font
— deferred), **no encrypted fixture** (pdf-lib cannot author encrypted
PDFs; the repository owns none — production tests mock the error).

## 3. Method (§11–§14)

- **Warm-up**: 1 warm-up run per engine/fixture, excluded from measurement
  — no cold-vs-warm comparison.
- **Measured runs**: minimum 5; fast cases (median ≤ 50 ms) extended to 10.
  Every executed case reached 10 runs; no case hit the 30 s budget.
- **Aggregation**: median (the reported value), mean, min, max, sample
  standard deviation, p95 (only when ≥ 8 samples). One fast run is never
  evidence.
- **Same bytes**: each fixture is built once per series and reused.
- **Determinism**: every series reported `metricsStable: true` — all
  measured runs of a case produced identical comparable metrics (timing
  excluded). Verified across all 88 series.
- **Resource bounds** (`bounds.ts`, tested): fixture ≤ 2 MB and ≤ 60 pages,
  iterations 1 warm-up + ≤ 10 measured, 30 s per-case budget, PDF.js task
  destroyed on every path (proved with an injected mock loader, including
  the rejected-promise path), no child processes.
- **Runtime**: Node v22.22.3, linux x64, recorded in the artifact with the
  generation timestamp. Timing values are measurements from one recorded
  run — reproducible in method, not identical in value.
- **Metrics**: 10 OBJECTIVE text/output metrics, 3 OBJECTIVE table metrics,
  1 HEURISTIC table metric (rowGroupingAccuracy), 1 HEURISTIC performance
  metric (heapDeltaBytes). No metric is called "fidelity". Full definitions
  in `src/lib/benchmarks/metrics.ts`.

## 5. Layout results (§8, §17 F)

- The current engine's text output carries **no positional information**,
  so direct engine-vs-engine X/Y-ordering comparison is **NOT MEASURABLE**.
  No positional score was invented for it.
- The objective, comparable proxy — the ORDER the reconstructed output
  exhibits — is `readingOrderAccuracy` / `columnOrderPreserved` (table
  above): candidate 1.00 on every layout fixture; current 0.00–0.44 on the
  five layout-sensitive fixtures (its output follows content-stream order).
- Candidate-internal positional accuracy is implicitly measured by the same
  metrics (row-major reading order can only be produced from correct x/y
  grouping).

## 6. Rendering results (§9, §17 G)

**Not evaluated — NOT APPLICABLE.** PDF.js raster output in Node requires
the optional native `@napi-rs/canvas` binary, which the production
no-native-binaries constraint excludes (and which the repository already
rejected when choosing pdfium for rendering). A capability probe confirmed
rendering works in-sandbox with the native canvas; no benchmark was run and
no visual-quality claim is made. pdf-to-jpg / pdf-to-png stay on pdfium.

## 7. Table results — extract-tables, component-level (§10, §17 H)

COMPONENT-LEVEL evidence: the candidate provides positioned text, not table
reconstruction. The benchmark scores a simple, documented grouping of
PDF.js positioned items (`engines/pdfjs-table-signal.ts`) against the same
CSV ground truth as the current engine. This is **not** full
extract-tables/pdf-to-excel equivalence.

| Fixture | Metric | Current | Candidate signal | Difference |
| --- | --- | ---: | ---: | --- |
| F-03 / F-31 / F-32 / F-33 / F-38 (all 5) | table.cellTokenRecall | 1.00 | 1.00 | tie |
| all 5 | table.rowCountRatio | 1.00 | 1.00 | tie |
| all 5 | table.rowGroupingAccuracy | **0.00** | **1.00** | candidate signal wins, 5/5 |
| all 5 | table.rowsExtracted (meta) | 4/10/4/12/6 | 4/10/4/12/6 | tie |

Root cause (verified from raw outputs): pdfium collapses the planted
3-space cell separators to single spaces, so the current whitespace
heuristic (split on 2+ spaces) returns **one cell per row** — row counts
are right, cell grouping is lost. PDF.js emits positioned items per cell
run; with the documented 6-unit gap threshold, the candidate signal
recovers the exact cell sets on all five shapes, including both
whitespace-run and positioned-cell tables.

## 8. Performance (§11–§12, §17 I)

Same machine, same bytes, 1 warm-up + up to 10 measured runs, medians
reported:

- Typical case: candidate ≈ **2× current** (median, across all 44 cases).
- Worst observed ratio: **12.5×** on the 30-page fixture (2.0 ms → 25.0 ms
  median).
- At the corpus bound (50-page stress fixture, equal to the production
  page limit): current 4.0 ms vs candidate 30.5 ms median, **p95 36 ms**.
- Small fixtures: ~1–3 ms medians for both engines.
- Heap delta (HEURISTIC, GC-noisy): candidate ≈ 10× current, worst
  observed 4.24 MB median on the 30-page fixture (current 155 KB).

Interpretation: the candidate is consistently slower and allocates more,
but the absolute cost at the production page limit is tens of
milliseconds — far below any user-perceptible or budget-relevant bound.
The Phase 71 DRAFT threshold "wall-clock ≤ 2× current" is **breached on
multi-page fixtures** (up to ~12×); the revised DRAFT threshold in §12
below bounds absolute impact instead.

## 9. Failures (§13, §17 J)

All observed failures, typed, with benchmark categories (no content in
errors):

| Fixture | Current | Candidate |
| --- | --- | --- |
| F-08-malformed | INVALID_PDF → malformed-input | InvalidPDFException → malformed-input |
| F-36-edge-truncated | INVALID_PDF → malformed-input | InvalidPDFException → malformed-input |

Both engines fail fast and typed on malformed/truncated input; neither
produces output for it. Two candidate content divergences are **not**
failures but behavioral differences:

1. **F-15 symbols — µ → μ**: PDF.js normalizes the micro sign (U+00B5) to
   the Greek small mu (U+03BC) during glyph mapping. The current engine
   returns the planted character exactly. One character in ten changed →
   unicodePreservation 0.9, exactness 0, one unexpected token.
2. **F-39 off-page text — page-boundary clipping**: for a text run whose
   glyphs extend past the page edge, PDF.js returns only the on-page part
   (`PDFKIT-OFFP` for planted `PDFKIT-OFFPAGE-1`); pdfium returns the full
   run. Discovered during fixture bring-up (the first F-37 geometry
   accidentally drew off-page), then captured deliberately in F-39.

## 10. QualityGate correlation (§15, §17 K)

QualityGate ran uniformly on every benchmark run (same production code):

| Engine | Verdict | Runs | Mean anchorPreservation | Mean tokenRecall |
| --- | --- | ---: | ---: | ---: |
| current-pdfium-text | healthy | 35 | 1.00 | 1.00 |
| current-pdfium-text | suspicious | 2 | — | — |
| candidate-pdfjs-text | healthy | 35 | 0.993 | 1.00 |
| candidate-pdfjs-text | suspicious | 2 | — | — |
| current-pdfium-tables | healthy | 5 | 1.00 | — |
| candidate-pdfjs-table-signal | healthy | 5 | 1.00 | — |

Observed relationship: **correlation is weak by design, and that is
correct.** `suspicious` appears exactly on the two marker-only fixtures
(scanned, blank) for BOTH engines — the gate detects "no real content"
identically. But `healthy` does NOT imply full content preservation: the
candidate's F-39 run (0.75 anchor recall) is `healthy`, because the gate
assesses structural validity, not planted-content preservation. Benchmarks
measure what the gate cannot see; the gate validates what benchmarks do
not. QualityGate thresholds were NOT modified, and no threshold should be
tuned to benchmark outcomes.

## 11. Privacy & security (§16, §17 L)

- The machine-readable artifact contains ids, versions, counts, ratios,
  typed codes, timing numbers and quality states only. `serializeReport`
  enforces the privacy contract (no anchors, no page markers, no content
  lines); `report.test.ts` re-asserts it, including a file write/re-read
  round-trip.
- The candidate performed full extractions with `globalThis.fetch`
  replaced by a throwing spy: **zero network calls** (candidate.test.ts).
- The PDF.js loading task is destroyed on every path — success, rejected
  load promise, mid-run page failure (mock-loader tests).
- Input buffers are copied before parsing; caller bytes are never detached
  (tested).
- No child processes, no filesystem writes from benchmark code (tested),
  no repository-tree side effects.

## 12. Per-conversion decisions (§18–§19)

No global GO was assigned. Aggregate averaging was not used; each decision
weighs that conversion's requirements.

| Conversion | Decision | Basis |
| --- | --- | --- |
| **pdf-to-text** | **CONDITIONAL GO** | Direct evidence: candidate wins reading order on every layout-sensitive fixture (5/5 at 1.00 vs 0.00–0.44) with content preservation at parity (37/39 fixtures identical; 2 documented behavioral divergences). Conditions: accept a bounded performance regression (≈2× typical, ≈8–12× on 30–50-page documents, p95 36 ms at the 50-page bound) and ≈10× heap delta; make a conscious call on the µ→μ normalization and page-boundary clipping behaviors. |

## 13. Production threshold draft (§20) — **DRAFT — NOT ACTIVE**

Proposed acceptance policy for a future pdf-to-text second engine. Not
wired into the router, not enforced anywhere, owner approval required
before any of it becomes policy:

1. Zero structural regressions: no new failures vs the current engine on
   the benchmark corpus (both must fail exactly the malformed fixtures,
   typed).
2. Content parity: `text.anchorPreservation = 1.0` and
   `text.anchorPrecision = 1.0` on every fixture where the current engine
   achieves it — with the two documented behavioral divergences (µ→μ,
   off-page clipping) requiring an explicit owner decision, not silent
   acceptance.
3. Layout win retained: `text.readingOrderAccuracy = 1.0` and
   `text.columnOrderPreserved = 1.0` on the layout fixtures.
4. Page coverage = 1.0; blank/image-only pages must stay honest
   (`blankPageCorrectness = 1.0`).
5. Performance (revised DRAFT — Phase 71's "≤ 2× current" is breached by
   measurement): median wall-clock ≤ 5× current on single-page/10-page
   fixtures AND p95 ≤ 250 ms at the 50-page bound. Absolute user impact is
   bounded; ratios alone are not the goal.
6. Heap delta median ≤ 5 MB at the 50-page bound.
7. No network access at runtime (already test-enforced).
8. No new production dependency without a separate dependency-policy
   audit: pdfjs-dist is a devDependency today; promoting it to
   `dependencies` is a Stage 4 decision requiring owner approval (bundle
   impact ≈ pdfjs legacy build, license Apache-2.0, zero transitive deps).

## 14. Recommended first Stage 4 conversion (§21)

**pdf-to-text.** Exactly one recommendation, based on evidence:

- Strongest direct evidence (the only direct-scope conversion).
- Clearly measurable benefit (reading order / column order on layout
  documents).
- Lowest implementation complexity: a like-for-like second adapter behind
  the existing engine abstractions — no new output format, no assembly
  stage, no reconstruction logic to port.
- Low security risk: pure JavaScript, in-process, proven offline, no child
  process, no native binary.
- Easy rollback: the router returns to the single current engine.
- Minimal architecture disruption: no API, artifact or contract change.

Explicitly NOT extract-tables for the first experiment, despite its
dramatic component numbers: it requires porting table reconstruction onto
positioned items (more engineering, more risk), while pdf-to-text is the
direct like-for-like role. Table work is the natural SECOND experiment.

## 15. qpdf boundary (§22)

qpdf was NOT integrated, installed or benchmarked in Phase 72. pdfjs-dist
received CONDITIONAL GO on pdf-to-text, so no qpdf benchmark is triggered
by this phase. qpdf remains the documented BACKUP candidate for
compress-pdf (a conversion pdfjs-dist cannot perform); if compress-pdf
improvement is ever wanted, a separate future phase must benchmark it —
including the child-process architecture its integration would require.

## 16. Known limitations (§R)

- **Synthetic corpus only.** Real-world PDFs (CID-keyed fonts, CMaps,
  tagged PDFs, OCR text layers, AcroForms, damaged-but-recoverable files)
  are not represented; pdf-lib-authored, standard-14-font documents cannot
  cover them.
- **Tamil untested** (WinAnsi fixture limitation); **encrypted PDFs
  untested** (no safe fixture source).
- **Timing** comes from one machine class, one recorded run; ratios are
  more meaningful than absolutes. p95 at 10 samples is approximate.
- **The candidate's reconstruction algorithm is ours** (y-buckets,
  60-unit column gap, 6-unit cell gap — all documented and tuned on this
  corpus). A different algorithm could score differently; the constants
  are part of the evidence, not ground truth.
- **heapDeltaBytes is HEURISTIC** (GC noise), as labeled.
- **QualityGate healthy ≠ content preservation** (see §10).
- **extract-tables / word / excel evidence is component-level**; assembly
  stages are unmeasured.

## 17. What Phase 72 did NOT do

No production engine registration, no live pdfjs engine, no fallback,
retry, ranking, switching, automatic or quality-based selection, no
`selectEngine()` change, no registry/router/API/UI/billing/auth/rate-limit/
concurrency change, no OCR, no AI comparison, no cloud processing, no
telemetry, no persistent document storage, no worker queues. The candidate
remains reachable only from `src/lib/benchmarks/` (test-enforced), and
pdfjs-dist remains a devDependency (test-enforced).
